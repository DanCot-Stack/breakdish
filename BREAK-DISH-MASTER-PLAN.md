## Status meanings

- **Live / production verified** — production operation was explicitly confirmed by the owner or an authorized prior verification. The source/date of that evidence is stated; this update did not recheck production.
- **Implemented / awaiting production verification** — code, schema and/or tests exist locally, but the complete live journey has not been confirmed in production.
- **In development** — local implementation or testing is underway and is not necessarily deployed.
- **Planned** — agreed work that has not been implemented.
- **Future consideration** — an idea that needs a product, legal, cost or technical decision before becoming committed work.
- **Blocked / requires decision** — work cannot be safely specified or finished until the listed decision or prerequisite is settled.

4. **Implement authoritative frame timing boundaries** — use match start and accepted frame completion boundaries, preserve original/replay timing evidence, and mark uncertain derived intervals unavailable or provisional rather than rewriting/fabricating them.
5. **Finish core result-derived launch functionality** — implement finalized-result standings, historically attributed Team/Singles/Doubles/Practice statistics, correct White Wash and agreed achievement treatment, and automatic statistics reports only when each dependency has a stable canonical result model.
6. **Keep Two-Club Beta gates explicit** — complete legal/privacy review, lifecycle verification, test-only/Casual exclusions, support and backup readiness before club onboarding.
7. **Bound the two-club beta to tested competition formats and workflows.** Keep public viewing separate from score editing; role labels alone must never grant match-scoring permissions.
8. **Prepare a reviewed release only after local gates pass and the owner approves.** Stage only intended tracked files; exclude local diagnostics, preview, assets, backups and tools. Fetch first and stop if GitHub moved. The prior owner-reported Render identities and Auto-Deploy settings must be reconfirmed before any later push/deploy.
9. **Manual production rollout, only after separate approvals:** fresh backup and target verification, API-first deployment and health/security checks, then Static Site deployment, then GET-only review of the existing test-only match followed by separately approved lifecycle writes. Never create another test match as part of this plan.
10. **After the stable core, prioritize future match types and advanced work** according to their dependencies and beta evidence. Casual Match is a planned functional mode with its own validation, privacy and zero-statistics requirements; tournaments, social, referee, rules, mobile and visual-polish work follow their respective acceptance gates.

These are roadmap priorities only. They do not authorize production access, production data changes, deployment, migrations or Git pushes.

### Frame Scoring & Achievements

**Current verified implementation:** an authorised scorer's `+` action currently submits the frame result directly. The active scoring interface also keeps Dish/Counter Dish and credited-player selectors visible. `completeFrame` writes the frame result and its optional Dish/Counter Dish event inside one database transaction, with the existing audit triggers recording the changes; the event table permits only `dish` and `counter_dish`, and current statistics views aggregate those two values. There is no One-Visit Clearance column/type, API validation, event or separate statistic. The current flow therefore does not yet meet the confirmation-popup requirement. Do not expose One-Visit Clearance in the UI until the database/API/statistics path exists.

**Required scoring interaction (planned):** when an authorised player activates the green `+` for the current frame, first open a confirmation dialog with **Normal frame win** selected by default, plus **Dish**, **Counter Dish** and **One-Visit Clearance** choices. Include the exact note: “A One-Visit Clearance is not a Dish. It is recorded separately.” **Confirm Frame** must submit the result and selected achievement as one server-authorised, transactional and auditable operation. **Cancel** must close the dialog without changing the match. Lock or otherwise deduplicate in-flight submissions so repeated clicks/network retries cannot create duplicate results or achievement records; keep server-side validation authoritative. Do not offer result/achievement submission for upcoming frames.

**Attribution and corrections:** for Singles, derive the credited player from the registered winning participant; never trust a client-supplied arbitrary player ID. For Team and Doubles, preserve the existing eligible frame-player selection and side rules, and require the credited player to be an eligible participant on the winning side under the configured format. The owner-confirmed invariant is at most one credited achievement per frame. If the authoritative qualification input identifies both Counter Dish and One-Visit Clearance, persist Counter Dish only; never count One-Visit Clearance as a Dish or Counter Dish. Enforce this in server/database validation, not only by offering a single-choice dialog. The existing unique `(match_id, frame_number)` event constraint already limits a frame to one current event, but its type constraint and API allow only Dish/Counter Dish. Corrections and retractions must use authorised existing match operations, recalculate all relevant totals consistently, and preserve the original event/result and correction history in the append-only audit trail rather than silently decrementing a counter.

**Remove redundant controls when the confirmed flow ships:** replace the always-visible active-scoring achievement and player-credit selectors with the confirmation dialog. Keep any necessary authorised correction workflow in the completed-frame history, clearly separated from awarding a new result. Ensure only the current eligible frame can be scored and that an upcoming frame cannot prematurely record an outcome or achievement.

**Scroll and focus usability issue observed:** after a frame is recorded, the browser has jumped toward the bottom of the Match Centre. After scoring, cancellation, or authorised retraction, preserve the scoreboard's viewport position and restore keyboard focus to a sensible control (normally the relevant score/action control or the next current-frame control). **Race-to competition rules (local implementation in development):** for league templates, fixtures and standalone matches, organizers select a positive integer target N. A repeating frame pattern of up to 99 steps is expanded authoritatively; exact lists are also limited to 99 entries to bound requests/editor controls. Migration 013 leaves existing targets NULL and does not infer or rewrite historical formats. The 99-step and bulk limits are implementation safeguards, not governing-body rules. **Race-to-Sets is planned as a separate engine stage:** use one agreed sets-to-win count S and one uniform first-to-F-frames target for every set in the match, with total maximum possible frames `(2S−1) × (2F−1) ≤ 500`; validate the combined match budget, never 500 per set. Preserve legacy all-configured-frames behavior for NULL-target records.
