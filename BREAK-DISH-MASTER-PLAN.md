This is the project roadmap, not a claim that every listed capability is live. It was reconciled against the local repository, README, API routes, frontend pages, migrations 001–012, available tests and the owner's latest production reports. Production and Render were not accessed for this update.

## Status meanings

- **Live / production verified** — production operation was explicitly confirmed by the owner or an authorized prior verification. The source/date of that evidence is stated; this update did not recheck production.
- **Implemented / awaiting production verification** — code, schema and/or tests exist locally, but the complete live journey has not been confirmed in production.
- **In development** — local implementation or testing is underway and is not necessarily deployed.
- **Planned** — agreed work that has not been implemented.
- **Future consideration** — an idea that needs a product, legal, cost or technical decision before becoming committed work.
- **Blocked / requires decision** — work cannot be safely specified or finished until the listed decision or prerequisite is settled.

## Current Priorities

1. **Prepare the reviewed local release** — after owner approval, stage only the nine tracked files listed by `git status`; exclude local diagnostics, preview, assets, backups and tools. Review the staged diff and secrets, fetch before pushing, and stop if GitHub has moved. Local `main` and cached `origin/main` currently match at `a292e27`.
2. **Deploy the API manually first after separate approval.** Auto-Deploy is owner-reported OFF. Verify API health, authentication/session, match detail, private-match permissions and the new audited frame-result DELETE route before changing the Static Site.
3. **Deploy the Static Site manually after the API checks pass and separate approval.** Confirm the production API origin and retain the current Static Site revision as the rollback baseline.
4. **Perform the GET-only production browser check** on the existing started test-only match. Use the saved match link and already authorized participant sessions plus a signed-out session; inspect only, and do not submit controls.
5. **After separate approval for writes, test the full lifecycle** on that same record: score, correction, confirmation, dispute/resolution, finalisation and audit. Do not create another match.
6. **Deliver confirmed-result standings and the essential two-club league journey.** Define points/tiebreaks and prove standings derive from finalized competitive team fixtures while excluding practice, money and test-only matches.
7. **Bound the two-club beta to tested competition formats and workflows.** Keep public viewing separate from score editing; role labels alone must never grant match-scoring permissions.
8. **After the stable core, prioritize future match types and advanced work** according to their dependencies and beta evidence. Casual Match is a planned functional mode with its own validation, privacy and zero-statistics requirements; tournaments, social, referee, rules, mobile and visual-polish work follow their respective acceptance gates.

These are roadmap priorities only. They do not authorize production access, production data changes, deployment, migrations or Git pushes.
